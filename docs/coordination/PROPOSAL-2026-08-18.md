## What I'd propose

### 1. Cut the machinery back to what two people need

With two agents who each own a repo and never touch the other's, most of the
coordination problem disappears. What's actually needed:

- **The failsafe line** — done. Both agents read status before working.
- **The mirror Doc** — so you can see both lanes from your phone. Worth it.
- **Issue #1** — where the two lanes talk to each other, in writing, versioned.

What I think we drop, or park:

- **The claim queue.** Built to share work among competing workers. There are no
  competing workers.
- **Wake agents.** Stays off. You open two chats; that was never the hard part.

### 2. Brainstorm at gates, not continuously

Before a project, end of P1, before P2, after P2. Not daily. The point of a gate
is that between gates the plan holds still.

### 3. Say it once

You tell whichever agent you're already talking to. That agent commits the
decision. The other reads it. You stop being the messenger — which is the actual
reason it has felt like nobody knows anything.

## The question I can't answer, and it's the big one

**What is the website supposed to deliver, and by when?**

Codex has P1-A — specific, shipped, testable. The website has no equivalent
written anywhere I can read. Gate-1's criteria appear in no document; I looked.
Everything I've built for the web lane is *infrastructure* — bridge, contracts,
guards, coordination — chosen by me because nothing told me otherwise.

That is the thing to brainstorm. Not the tooling.

Some possible answers, to argue with rather than pick from:

- **Guest Play is the product.** A teacher shares a link, a student plays, a
  result comes back. Everything else is later.
- **The teacher side is the product.** Making activities is the hard part and
  the reason anyone pays.
- **The website is a shell.** The game is the product; the site just hosts and
  shares it, and should stay small deliberately.

These lead to genuinely different websites. I've been building as if the first
one is true.

## What I'd do first, if you asked me today

One real round trip between a Unity build and the website:
`ready → boot → mode-selected → session-started → session-finished`.

It validates the event name, the receiver, the JSON shape and the dedupe all at
once, and it's the only thing standing between "specified and tested" and
"proven to work". Everything else in the web lane is guesswork until that runs.

It needs a Unity build with a C# receiver — so it's a Codex dependency, not
something I can start alone.
