# SAL0MANder Tutoring Portal — Phase 1 Demo (PR 1–PR 7)

**DEMO ONLY — fictional families, local-only storage, simulated email.** Not deployed, not connected to any real account, email service, payment provider, or model API.

## What is simulated
- **Accounts & sign-in:** Fictional seed actors (3 households, 5 children using first names only, Mr. Sam as owner+admin+mentor, Mentor B assigned to Elena's household, Mentor C unassigned). Email-link sign-in drops a simulated link into the in-app Inbox panel; zero real email is sent.
- **Consent:** Simulated verification methods (signed form scan or short verification call) with saved notice version and timestamp. Not a legal COPPA verification flow.
- **Storage & work failures:** `LocalPortalStorageAdapter` (`localStorage` key `sal0mander.portal.demo.v1` with in-memory fallback) behind `PortalStorageAdapter` so Phase 2 swaps in a real backend. Worksheet failure buttons simulate a dropped save (`Not saved, retrying…`, no loss) and an external-device edit conflict (newer wins, visible alert).
- **Ask rail, Nov 25 approval layers & sign-in guards:** Text + 1 work photo placeholder ("cover your name", 30-day retention note, never uploaded). **Review-first only (no Auto-send)** for teens: every teen question goes to the verified parent email with a single-use ~72 h approve link. Release requires either (a) approve link + fresh 6-digit one-time code sent to the verified parent email (blocked on teen-registered/remembered devices) or (b) an email forward **FROM** the verified parent address (forwards from a teen address are rejected). Approved questions receive an `"Approved by parent, date and time"` stamp required for Mr. Sam to open, trigger a `"Was this you?"` email with one-tap pull-back & approval lock, flag fast/same-device/same-network approvals in Mr. Sam's queue, and append to an immutable append-only approval log visible only to the household parent and Mr. Sam. Parent email changes require old-address confirmation + a 48-hour hold. Remembered teen Chromebooks auto-sign-in to the teen's own profile via PIN only (revocable by parent), and a forwarded parent sign-in link reaches only the profile chooser + teen PIN profile (never parent powers). Adults (18+) bypass parent approval layers.
- **How to test:** Run `npm run test` (or `npx vitest run src/portal/`) to verify all 14 access assertions, all 9 Nov 25 approval layers, and the two new acceptance rows.
- **Mentor view, Belts & Admin:** Dedicated Mentor View (`Today`, `Kids`, `Friday`, `Rooms`, `Script library`) and admin-only `Admin` tab. Per-course belt ladders (7th grade = 7 units/stripes, belts at 2/4/6/last + live teach-it test for Black), computed stripes on reviewed work, human-only logged belt awards (never automatic), cosmetics-only points, starter badges (`First question`, `Explained it`, `Came back`), and one-sentence parent belt summary (no charts).
- **Game rooms (placeholder, no real multiplayer):** Mentor invites child (blocked during scheduled tutoring windows; respects standing-yes) → parent email approval (`Yes`, logged) → room opens only when mentor starts it → countdown clock, 60-second warning, hard end & goodbye screen, leave/rejoin while running, join refused when not invited/before open/after end.
- **Mentor access boundary:** Mentor B/C access is fictional-data demo only until counsel reconciles mentor access (`KID-SAFETY-RULES.md` B2/B6 currently limit real access to Samuel).

## How to run the demo & Access Checks
1. **Browser:** Run `npm run dev` and open `/portal`. Switch between **Access Checks**, **Parent Account**, **Child Profile**, **Mentor View**, and **Simulated Inbox**.
2. **Automated suite:** Run `npm run test` (or `npx vitest run src/portal/`) to verify all 11 access assertions, parent account flows, child profile/worksheet persistence, Ask rail delivery gates, Mentor/Admin views, belts/badges, game rooms, and route rendering.
